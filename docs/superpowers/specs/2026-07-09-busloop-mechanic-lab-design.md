# BusLoop 机制实验台设计

## 目标

将现有 BusLoop 可试玩广告工程改造成面向游戏设计与机制体验的实验台。工程不再包含广告跳转、安装引导或平台打包逻辑，同时保留当前 BusLoop 核心玩法、Three.js 场景、声音、胜负流程、重置、调参编辑器和自动化测试。

第一版提供一个可扩展的机制选择框架，预置 10 个已讨论机制。基础规则可实际试玩，其余机制先提供完整的说明入口和待实现状态。

## 选定方案

采用“机制注册表 + 单一实验台运行时”。

- 机制注册表保存 `id`、名称、分类、状态、说明、理解难度和运行时创建入口。
- 页面壳层只读取注册表，不直接包含具体机制规则。
- 当前 BusLoop 实现迁入基础机制模块。
- 后续机制各自使用独立目录，通过统一接口创建关卡和运行时。
- 不使用入口文件中的大型条件分支，也不为每个机制复制一套页面。

该方案优先支持机制独立验证，同时保留未来做机制组合的扩展空间；第一版不实现机制组合。

## 页面结构

桌面使用三栏：

1. 左侧 `MechanicLibrary`：搜索、分类、机制条目、实现状态和当前机制说明。
2. 中间 `MechanicStage`：加载并运行当前机制，承载真实游戏画布、加载状态、胜负结果和重置。
3. 右侧 `SceneEditor`：复用现有调参编辑器，默认折叠。

窄屏下：

- 机制库进入左侧抽屉。
- 场景调参进入独立工具抽屉并默认关闭。
- 游戏画布始终获得主要可视区域。

页面风格保持工具化、安静和高信息密度，不使用营销式标题、广告按钮或产品下载文案。

## 交互

- 首次访问默认选择 `base`，加载当前基础关卡并允许完整操作。
- 左侧按 `基础 / 信息 / 空间 / 奖励 / 目标 / 策略` 分类，支持按名称搜索。
- 条目使用文字状态 `可试玩` 或 `待实现`，不只依赖颜色。
- 选择待实现机制时，左侧显示机制效果、体验变化和理解难度；中间保留基础盘面的冻结预览，暂停输入并显示说明覆盖层。
- 待实现覆盖层提供“返回基础规则”命令。
- 选择可试玩机制时执行统一生命周期：销毁旧实例、创建机制数据、创建游戏和视图、恢复输入与调试接口。
- 当前机制写入 `?mechanic=<id>`；刷新和分享后保持选择。
- 未知或缺失的机制 ID 回退到 `base`。

- `src/styles.css`：增加三栏、抽屉、机制状态和覆盖层样式，移除 CTA 样式。

具体文件拆分可在实施计划中根据现有测试耦合做小幅调整，但不得把机制规则重新集中到 `main.js`。

## 状态与错误处理

- 机制 ID 不存在：记录开发警告并回退到 `base`。
- 待实现机制：不创建对应机制实例。若当前已有基础实例则冻结并保留画面；若通过 URL 直接进入，则先创建基础预览再冻结。说明覆盖层显示期间画布输入被禁用。
- 机制切换失败：清理半创建实例，显示可恢复错误并提供返回基础规则。
- 切换与重置必须显式销毁旧监听器、动画和视图资源，避免重复订阅或多个动画循环。
- 机制选择和场景调参存储使用不同键，避免互相覆盖。

## 测试与验收

自动化：

- 机制注册表包含 `base` 和 10 个预置机制，ID 唯一且元数据完整。
- 查询参数选择、刷新保持、非法 ID 回退正确。
- 待实现机制不会接收游戏输入。
- 基础规则切换、重置、胜负、声音和现有调参保存不回归。
- 切换生命周期不会留下重复订阅或动画循环。
- `npm test` 与 `npm run build` 通过。
- 仓库活跃代码不再包含 `mraid`、商店链接、`InstallFullGame`、`Play Now` 或 AppLovin 打包入口。

视觉与手动验证：

- Playwright 检查桌面三栏和手机抽屉布局。
- 确认画布非空、车辆可点击、控制区不遮挡主要盘面。
- 检查长机制名称、搜索无结果、待实现说明、胜负面板和加载状态。
